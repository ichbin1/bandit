# Метацикл обучения на многоруком бандите

Исследовательский код для гипотезы из `Метацикл обучения.docx`: агент, который
тратит часть шагов не на «добычу» награды, а на **инвестиции** (данные →
множитель → технологии → новые руки), может обгонять агента, который всё время
только тянет руки. Пакет `bandit` — это воспроизводимая среда для проверки
такой гипотезы: стабильные id действий, сериализуемые конфиги, парные сиды,
метрики и графики.

## Быстрый старт

```powershell
pip install -r requirements.txt          # numpy, matplotlib, pytest
python -m bandit.cli list                # что есть: среды, агенты, политики, наборы
python -m bandit.cli demo                # 7 конфигов × 5 прогонов × 1500 шагов + графики
python -m bandit.cli run --suite pyramid-ablation --runs 30 --jobs 4
python -m bandit.cli run --suite pyramid-learned --runs 30 --jobs 4
python -m bandit.cli run --suite pyramid-hypotheses --runs 30 --jobs 4
python -m bandit.cli run --suite pyramid-overload --runs 30 --jobs 4   # H6
python -m bandit.cli show results/demo   # сводка по сохранённому каталогу
python -m bandit.cli stats results/demo/runs.csv   # парные тесты + Холм
python -m bandit.cli report results/demo           # report.md + report.json
pytest                                   # тесты, включая golden-тесты версии 0.1
```

Каждый прогон сохраняется в `results/<run_id>/`:

| файл | что внутри |
| --- | --- |
| `<config>.npz` | все массивы `(n_runs, n_steps)` по полям `RECORD_FIELDS` |
| `<config>.json` | манифест конфига + пары сидов (полная воспроизводимость) |
| `manifest.json` | версия пакета, git-коммит, команда, число прогонов |
| `metrics.csv` | сводка метрик: среднее, SEM, 95% ДИ |
| `runs.csv` | по одному прогону в строке — вход для парных тестов |
| `results.csv` | парные сравнения с базлайном (`bandit.cli stats`) |
| `report.md`, `report.json` | сводный отчёт и вердикты H1–H6 (`bandit.cli report`) |
| `dashboard.png` | 2×2: очки, сожаление по рукам, частота лучшей руки, эпохи |

Проверка паритета с версией 0.1 (те же числа при тех же сидах):

```powershell
python scripts/check_parity.py
```

Модули 0.1 import-совместимы по смыслу, но не по именам: например,
`run_pyramid_experiment` заменён на `run_config`, а `env.pull(n_arms + k)`
теперь надо писать как `env.pull_legacy(n_arms + k)` или через
`meta_action_id(MetaAction.BUY_ARM)`.

## Что изменилось относительно версии 0.1

1. **Стабильные id действий.** Руки — `0 .. n_arms-1`, мета-действия —
   `10_000 + вид`. Раньше мета-действие кодировалось как `n_arms + k`, и после
   покупки руки один и тот же `int` означал другое действие: траектории нельзя
   было сравнивать постфактум. Теперь `env.step(n_arms)` падает с `ValueError`
   и подсказкой — молчаливой интерпретации нет.
2. **Агент и мета-политика разделены.** Агент выбирает только руку; политика
   решает, когда инвестировать. Это даёт матрицу «агент × политика» и честную
   абляцию (`gate_only`, `amp_only`).
3. **Оракулы.** `pyramid-oracle-none` и `pyramid-oracle-full_cycle` видят
   истинные средние (`expose_oracle=True`) и задают верхнюю границу.
4. **Записи шага.** `RunRecords` хранит 19 массивов: действия, вид действия,
   награду, очки, состояние экономики до/после, истинные средние, `arm_regret`,
   `useful_gained`/`info_gained` (поток информации для H6).
5. **Reward ≠ points.** Агент учится на базовом сигнале руки `0/1`; множитель
   попадает только в очки. Иначе агент оптимизировал бы экономику вместо
   качества выбора, и сравнение алгоритмов по награде теряло бы смысл.

## Метрики

Классическое сожаление здесь не определено: среда меняется действиями агента,
«лучшая рука» — движущаяся цель. Поэтому отчёт даёт три величины:

* `cumulative_arm_regret` — недобор из-за выбора руки (`μ*(t) − μ(a_t)` до
  действия, мета-шаги исключены);
* `efficiency` — очки / очки оракула при **тех же сидах**: доля выхлопа
  идеальной политики (оракул тоже платит за метацикл);
* `point_regret(t)` — пошаговый разрыв с траекторией оракула (для графиков).

Плюс: `steps_to_epoch_1/2`, `final_epoch`, `final_n_arms`, `final_multiplier`,
`arm_pull_share`, `points_per_pull`, `auc_normalized`, `steps_to_50pct/90pct`,
`points_after_epoch_1` (очки уже после выхода в эпоху 1 — метрика для H4),
`useful_info_share`/`junk_info_share` (доля сигнала и мусора в информационном
потоке — шкала режима перегрузки для H6).
Бюджет ветвей метацикла: `conversions`, `arm_buys`, `gate_crafts`,
`amplifier_crafts`, `meta_step_share` и вклады в множитель
`multiplier_from_conversions/arms/gates/amplifiers`. Сумма четырёх вкладов
равна `final_multiplier − 1` (закреплено тестом), поэтому видно, какая ветвь
собрала выигрыш, а не только его величину.
Подробности и предсказания — в `docs/HYPOTHESIS.md`.

## Парная статистика (`bandit.cli stats`)

Все конфиги одного прогона идут на **одних и тех же** парах сидов, поэтому
сравнивать их надо парно: дисперсия разности ниже, чем у разности независимых
выборок. `bandit/stats.py` (numpy, без scipy) даёт:

* `bootstrap_mean_ci` — перцентильный интервал среднего;
* `paired_bootstrap` — интервал и p-value для средней парной разности
  (p никогда не равен нулю: поправка `(k+1)/(n_boot+1)`);
* `wilcoxon_signed_rank` — знаковые ранги с поправкой на связи;
* `sign_test` — точный биномиальный тест «кто чаще выигрывает»;
* `holm` / `holm_dict` — контроль FWER по семейству сравнений;
* `load_runs_csv` / `write_results_csv` — обмен через `runs.csv`/`results.csv`.

Bootstrap инициализируется явным сидом (`DEFAULT_SEED = 20240501`), поэтому
таблицы воспроизводятся побитово:

```powershell
python -m bandit.cli stats results/demo/runs.csv --method wilcoxon --metric final_points
```

## Отчёт (`bandit.cli report`)

`bandit/report.py` читает `runs.csv` + `manifest.json` и собирает
`report.md`/`report.json`: таблицу «среда × агент × политика», парные сравнения с
поправкой Холма и **автоматические вердикты H1–H6** с числами, на которых они
основаны. Статусы: `подтверждена`, `частично`, `опровергнута`,
`не подтверждена` (эффекта нет, но и обратного значимого эффекта тоже),
`нет данных` (в прогоне нет нужных конфигов или метрик: отсутствие
эксперимента не считается аргументом против гипотезы). Правила вердиктов
описаны в `docs/HYPOTHESIS.md`, раздел 6.

H1–H5 считаются только по «чистым» средам, H6 — только по режимам
`pyramid-overload-*`: метацикл должен оставаться выгодным, когда поток
информации избыточен и зашумлён (`--suite pyramid-overload`, 6 режимов ×
6 конфигов, параметры — в `bandit.configs.INFO_REGIMES`). Оракул для H6
ищется по спецификации среды (`env.params`), сидам и горизонту, поэтому
`efficiency` считается в каждом режиме, а не только в базовом прогоне.
Если прогонов на конфиг меньше 10, отчёт печатает предупреждение: вердикты
предварительные (мало пар для устойчивых p-value).

## Преимущество метацикла (S0/S1/S2/S6)

Отдельные стадии отвечают не «работает ли метацикл», а «из чего собран
выигрыш и где он кончается»:

```powershell
python scripts/advantage_sweep.py --list
python scripts/advantage_sweep.py --stage s2 --runs 5 --out results/_adv_dry
python scripts/advantage_sweep.py --all     # s1, s2, s6 со своими n и горизонтами
python scripts/advantage_report.py          # results/advantage.md + .csv
```

* `s1` — экономика: оси `engine` (`arm_bonus_increase`), `cap` (`max_arms`),
  `lv` (`n_levels`), контраст `none` vs `full_cycle`;
* `s2` — абляция ветвей: `mult_only`, `gate_only`, `amp_only`, `amp`,
  `full_cycle` и оракулы;
* `s6` — длинный горизонт (T = 10 000): профиль Δ(t), момент `t*` (после
  которого преимущество не меняет знак) и устойчивость к агенту (`greedy`,
  `random`);
* `s0` — дешёвый дым конвейера.

Имена конфигов — `pyramid-adv-<ось>-<уровень>-<агент>-<политика>`; они
регистрируются в `bandit.configs.REGISTRY` и запускаются обычным
`bandit.cli run`, поэтому результаты лежат в том же формате (`*.npz`,
`runs.csv`, `metrics.csv`, `manifest.json`). Отчёт даёт Δ с поправкой Холма,
бюджет ветвей, Δ на сетке горизонтов и вердикты M1–M8 (статус `н/д`, если
нужной стадии нет в отчёте).

## Воспроизводимость

* Парный дизайн: пары сидов `(env_seed, agent_seed)` генерируются один раз и
  используются всеми конфигами одного прогона (`make_seed_pairs`).
* Порядок обращений к RNG в `LayeredPyramidBandit.reset` и в
  `Agent._argmax_random` сохранён как в версии 0.1, поэтому golden-тесты
  (`tests/test_golden.py`) фиксируют точные значения очков на 3000 шагов.
* Конфиги — обычные словари, без лямбд: `--jobs > 1` работает на Windows
  (spawn) без pickle-ошибок.
* `results/` в `.gitignore` и не должен синхронизироваться OneDrive.

### Обучаемая мета-политика (P4)

`bandit/meta/learned.py` — контекстный UCB-мета-бандит с отложенной наградой:

* опции — мета-действия, которые среда разрешает прямо сейчас (`can_*`);
  воздержание задано *базовым уровнем*: инвестиция выбирается только если её
  UCB-оценка выше нуля (иначе окно измерения «съедало» бы инвестиции просто
  из-за расписания решений);
* контекст — `(эпоха, класс доступных инвестиций)`;
* награда — лог-отношение доходности соседних окон
  `log((y_after + eps) / (y_before + eps))`: масштабно-инвариантна и не
  «вознаграждает» общий рост множителя (иначе выучивается «никогда не
  инвестировать»);
* политика детерминирована (без RNG), поэтому `--jobs 1` и `--jobs 2` дают
  одинаковый результат.

Замер (`--suite pyramid-learned`, 8 сидов, 3000 шагов, `window = 5`):

| агент | none | full_cycle (ручной) | learned (обучаемый) |
| --- | --- | --- | --- |
| ucb1 | ≈ 2.6 тыс. | ≈ 76.1 тыс. | ≈ 75.8 тыс. |
| eps0.1 | ≈ 2.5 тыс. | ≈ 77.3 тыс. | ≈ 77.3 тыс. |

Политика, не знающая правил экономики, догоняет ручной жадный метацикл (> 0.99
от него) и на порядок превосходит отказ от инвестиций. Абляция горизонта
(`learned_slow`, `window = 8`) роняет результат до ≈ 60 тыс.: измерять
отложенную выгоду слишком долго — значит инвестировать редко.

Дальше: P6 — визуализация обучения `learned` (динамика UCB-оценок по эпохам) и
более широкий набор контекстов (например, «сколько тиров рецепта осталось»).
